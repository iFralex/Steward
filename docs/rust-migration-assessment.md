# Rust migration assessment for Steward

**Assessment date: November 13, 2026.** The purpose of this study is to decide where a Rust implementation is worth investigating, not to migrate every component. Measurements use a Mac mini M4 with 16 GB unified memory and the installed Steward services. They describe this workload and these conditions; they are not general language benchmarks or production guarantees.

The strongest result is not a language comparison: Action Center repeatedly called an unavailable remote model and performed local flow embeddings before those calls. The resulting backoff and Mail query indexes have since been deployed; their initial observations are recorded below. A Rust Usage worker is the only candidate here with a direct prototype-to-Node comparison on the same real snapshot; MIME parsing merits a controlled prototype, but has not yet been compared with Rust.

## Scope and safety

I launched fresh instances of the **installed MCP server bundles** and made real read requests over their stdio MCP protocol. The tests covered **31 distinct read tools out of 51 listed** by eight servers: Mail, Calendar, Contacts, Documents, Shell, Action Center, LLM Wiki and Trains. Mail, calendar, contacts, action and wiki reads used actual local stores or the running wiki API. Documents and shell used a temporary synthetic text file. Train lookup and status used the public ViaggiaTreno service; no train reservation or mutation was performed.

I did not execute sends, replies, cancellations, writes, deletes, wiki rescans or window changes. Voice call tools were not invoked; the host's read-only `/voice/status` endpoint was measured, which is not the same as the voice MCP `call_status` preflight. The separate voice process and agent-model turns need their own evaluation. A selection of existing validation and command-policy tests ran against isolated fixtures: **93 passed**. These are not a substitute for testing actual writes in a disposable environment.

MCP responses can contain personal data. Benchmark scripts retain timings, aggregate counts, sizes and status only; returned content and identifiers are not saved. The generic query `project` was sent to the configured local `local-embed` model. The tests forced local embedding endpoints rather than allowing arbitrary remote overrides. These local embedding calls add zero-cost records to the gateway ledger. No paid LLM calls or emails were initiated by the benchmarks.

For most MCP cases there was one initial call and three subsequent calls in the same process. These are descriptive samples, not statistically reliable p95 measurements. A fresh server per category isolates startup but is not the existing host's already-running connector. Background jobs and models remained active; cold OS caches were not controlled. The first slow call may include startup, index preparation, model loading or I/O: the measurements alone do not identify which. RSS is not unique physical memory and excludes child processes and GPU allocations.

## Background programs: the largest finding is retry behavior

In the rolling 24-hour Usage window sampled at 22:10 UTC, the ledger recorded:

| Action Center activity | Calls | Recorded positive-cost calls | Sum of recorded durations |
|---|---:|---:|---:|
| `scan`, DeepSeek Flash, HTTP 402 | 7,043 | 0 | 4,345,526 ms |
| `flow-retrieval`, local BGE-M3, HTTP 200 | 7,044 | 0 | 1,716,754 ms |
| `flow-retrieval`, HTTP 502 | 3 | 0 | 3,691 ms |

The same rolling ledger window contains 142 `scheduler.action-center` entries totaling 6,622,106 ms, including four recorded errors. The sums of the two request types are comparable in magnitude to the scheduler total. The windows are timestamp-filtered independently and can include partial jobs at the edges, so this is strong evidence of where time goes, not a precise per-run CPU profile. Recorded zero cost is a ledger observation, not provider-invoice reconciliation.

The source at the time of this observation explains the pattern: a candidate's flow search and local embedding occurred before remote analysis; a gateway failure threw, and the candidate was deliberately left unseen for retry. Action Center did not yet have its own global gateway backoff, so it could retry failed candidates on subsequent cycles. The mail-promoter had separate global and per-thread backoff, which did not automatically cover Action Center. The Action Center backoff has since been deployed, as described below.

The assessment recommended persistent, observable Action Center backoff for availability/authentication/credit errors, with bounded probes while preserving pending candidates and independent local work. The subsequent release implemented that behavior; comparison of billed calls, failures and scan duration after provider recovery remains future work.

Completed scheduler log entries from the same day showed median / empirical p95 of 26.7 / 45.1 s for `mail-distill` (91 entries), 26.0 / 39.5 s for `mail-reconcile` (138), 46.7 / 52.9 s for Action Center (137), and 4.45 / 50.1 s for mail embedding (93). These are wall times of different workloads, not CPU times or matched runs. They do not establish which language dominates.

### Mail promoter: test the algorithm before porting it

The production path constructs and cleans a thread before comparing its source hash with the prior state. A read-only experiment ran the actual thread builder and hash against a direct subject/body hash on **44,939 threads**, alternating which path read first. Every hash matched. The state snapshot contained 33,676 unchanged, 11,107 changed and 156 without previous state; the two databases were independently read and are not one atomic cross-database snapshot.

In one warm observation, building and hashing the unchanged threads took 5.20 s, versus 1.09 s for the direct hash. Across the whole measured subset the current build-and-hash phases totaled 7.59 s. A **calculation** that uses the direct hash for all threads and then still builds the full input for changed/missing threads gives 3.78 s for these phases. It is not a measured full job: it combines per-stage timings, excludes later routing and writes, and changed threads would be read twice. A previous observation under different cache conditions was substantially slower. Retest end-to-end with a consistent snapshot and realistic cache conditions before claiming a saving.

A safe implementation would also need to preserve ordering, concurrent updates, malformed data/error behavior, attachments, policy invalidation and deferred outcomes. The test verifies hashes on this dataset; it does not prove full behavioral parity. **Try this design in TypeScript first** and evaluate a Rust implementation only if the remaining measured bottleneck justifies it.

A subsequent prototype ran `processThread` over 44,940 real threads using read-only mirror/state snapshots, simulated in-memory state and a forced junk role for every changed thread. The current and hash-first implementations produced identical counts and recorded hashes: 33,659 unchanged skips, 11,281 filtered and zero exceptions. Their observed wall times were 7.76 s and 5.85 s, respectively. The hash-first run was second, so OS cache favors it; changed threads did not execute actual GTE, attachments, triage or writes. This is not a full production backfill benchmark.

The existing ten `run.test.ts` tests passed against the prototype, but targeted in-memory adversarial cases found a real semantic difference. An unchanged thread with malformed recipient JSON raises `SyntaxError` in the current implementation; an out-of-range date or an invalid numeric HTML entity can raise `RangeError`. Hash-first instead returns `skipped` in all three cases, without building the input. It could therefore suppress errors that the current batch reports as deferred. Validating only JSON would not preserve the existing behavior: date formatting and body cleaning can also fail. **The prototype has not been applied to the pipeline.** Preserving or deliberately changing validation, concurrent-update behavior and policy invalidation requires a separate design and tests.

A guarded prototype validates metadata and dates and falls back to full construction for suspicious numeric entities, malformed values or non-string bodies. It preserved the errors in those three adversarial cases and passed the ten existing `run.test.ts` cases. In three alternating-order, local-only simulations on 44,941 real threads, its baseline and guarded paths had identical outcomes and recorded hashes; median measured process-thread time was 11.92 s versus 8.69 s. Changed threads were forced to the local junk filter, with in-memory state: this does not time the real batch with model work, attachment handling, state writes or concurrency, and it is not proof of complete parity. A separate prototype that fetches each thread's messages in one query, without skipping construction, matched complete inputs on the same 44,941 threads and took 15.89 s versus 17.32 s in that observation. It also needs concurrency and malformed-data tests before production use.

The promoter audit for 90 batches in a separate 24-hour window recorded 1,004 new GTE checks, 969 actual scores and 888,311 cache hits. These are repeated observations across cycles, not unique threads. It also recorded 16 gateway requests and 16 gateway failures. Local filtering, provider calls and billed calls must be reported separately.

### Mail reconciliation and Action Center selection

A single read-only partial reproduction of `mail-reconcile` observed 79,190 `.emlx` paths: filesystem enumeration took 3.68 s, loading 79,189 known paths 0.75 s, selecting the 50 stale-extraction candidates 6.04 s, and comparing mtimes 1.01 s. This did not ingest, delete or write state. The production locator suppresses inaccessible-directory errors, so completeness cannot be guaranteed by the count alone. These phases are not independent of page cache or the sampled scheduler timings.

SQLite's plan for the stale-extraction query was `SCAN messages` plus `USE TEMP B-TREE FOR ORDER BY`. The Action Center recent-mail query had the same plan. An in-memory experiment materialized anonymous metadata from 79,796 real rows, then compared candidate identities and order against the original read-only queries and partial indexes: all 50 stale and 300 action candidates matched. On precomputed metadata, seven-sample median selection changed from 2.67 to 0.0040 ms for stale records and from 2.05 to 0.0216 ms for action candidates. This is **not** a prediction that the 6-second production query becomes 0.0040 ms: it excludes metadata construction, full payload reads, disk I/O, index maintenance and schema migration. It supports testing an indexed representation or queue before porting SQLite callers to Rust.

A further test used a **726 MiB private disk copy** of the actual relevant columns for all 79,796 messages; the full 6 GiB database, remaining columns, indexes, triggers and FTS were not copied. The temporary copy was deleted after testing to recover disk space; aggregate measurements remain. Candidate IDs and ordering matched before and after indexes. A broad stale-date index did not improve the warm samples (about 75–78 ms before versus 78–90 ms after). A partial index for the version-2 stale predicate reduced four samples from 75–165 ms to 0.009–0.091 ms; the existing parameterized query used it at version 2, while version 3 correctly fell back to the scan. A partial Action Center date index reduced selection-only samples from 42–44 ms to 0.024–0.069 ms. These measurements fetch IDs, not the actual full payload, and do not control the OS cache. Building both candidate partial indexes on the copy took 1.79 s; five rollback-only trials updating 500 recent rows took 4.48–15.84 ms without indexes and 10.99–13.06 ms with them. This is not a production write benchmark. Before adopting indexes, test the full database and migration, JSON edge cases, write amplification and replacement of the version-specific index when the extractor version changes.

The current stale backlog also exposed a correctness issue: of 50 selected messages, 36 had a missing primary `emlx_path`, but all 36 had a different registered path that existed. Reconciliation previously checked only the primary path, so these messages could repeatedly occupy the 50-item window without being re-extracted. The deployed code now selects a surviving registered path, preferring full copies, and tests cover re-extraction with an unchanged mtime and a vanished primary. It can advance the backlog and change extracted text, so monitor downstream thread re-evaluation and provider costs. Unavailable paths with no surviving alternative can still occupy the limited candidate window and need separate handling.

On November 14, a read-only census found 19,943 stale messages in 9,895 threads. Only 36 messages had a missing primary and a surviving alternate: 16 had a full alternative and 20 only a partial alternative. The other 19,907 had an accessible primary and are part of the existing extraction backlog, not newly caused by the fix. The locator used by reconciliation also found all 36 alternates in the sampled 50. The 20 partial alternatives were all already stored as partial bodies. The fix now refuses a partial alternate when the stored body is full, to avoid degrading it; a regression test covers that case. The parser successfully read all 36 alternatives: 34 extracted texts differed from stored text, and five of the partial alternatives produced shorter text. Length alone does not establish quality.

Simulating replacement of subject, body and date for those 36 messages yielded 18 distinct affected threads, 16 with changed source hashes. Comparing with the independent promoter-state snapshot, 15 previously unchanged threads would become pending (13 previously promoted, two skipped); one changed thread was already pending. Two threads' hashes did not change. These are snapshot simulations: actual timing, other messages, cached gates, attachment decisions, remote failures and paid requests can change the outcome. The count does not predict billing or imply the prior decisions were wrong.

A stronger index experiment copied all columns and existing indexes of 79,798 real message rows to a private temporary database, then ran the actual query projections and compared ordered message IDs. Median of five uncontrolled-cache observations was 161.82 to 0.035 ms for stale selection and 49.44 to 2.33 ms for Action Center selection. Five rollback-only updates of 500 recent rows had median 6.43 ms with existing indexes versus 10.09 ms with candidate indexes. Building the two candidate indexes took 0.51 s on that copy. This excludes FTS, other tables, triggers, real ingestion and cold-cache control. The partial stale index is tied to extractor version 2; when the parameter becomes 3 the planner falls back to a full scan. The live read-only snapshot contained zero invalid extraction JSON values among 78,776 eligible rows, but future data and schema upgrades still need migration and maintenance tests. The private copy was deleted after measurement.

Further disposable-database integration tests verified index selection after updates and deletions, the version-3 fallback, rejection of malformed extraction JSON without leaving an index, and WAL snapshot isolation across a concurrent writer. All three passed. These tests did not cover the production schema migration or full ingestion; at that stage no production index had been added.

**Deployment update:** release `2026-11-14T01-57-30-605Z-8d59c31c` creates the candidate indexes when a writable Mail store opens. The stale index name includes the extractor version; old version indexes are retained for older processes, and failure to create an optional index is logged without preventing store startup. On a private full-column copy, the actual migration preserved complete query results and took 517 ms. In a single production read-only snapshot after deployment, indexed and forced-scan queries returned identical complete results; stale selection took 4.47 versus 338.57 ms and recent-message selection 3.15 versus 66.66 ms. These are single, uncontrolled-cache samples, not full-cycle savings. The two indexes occupied approximately 1.18 MiB total. A pre-update operational backup is stored on ORICO. Rollback requires reverting the application before dropping indexes, since the updated writable store recreates them.

A partial read-only Action Center profile saw 300 recent messages, 204 not found in the seen set, and 458 seen IDs; the production path applies additional candidate filters and may operate under different state at another moment. A separate calendar matching probe saw two upcoming events and 76 calendar actions, with less than 2 ms spent on the sampled repeated query and matching. Calendar automation was disabled in the inspected configuration, so this is not an explanation of the measured Action Center runs.

## Other programs

**MIME extraction.** The current extraction source and mailparser taken from the installed bundle were run in memory on 60 real `.emlx` files: 20 recent files in each of three database-size bins, excluding actual files over 4 MB. Median parsing times were 8.65, 22.17 and 92.26 ms; empirical p95 values within each 20-file bin were 22.47, 29.83 and 168.05 ms. The median actual file sizes were approximately 31, 95 and 351 KB. This is a selected sample, not a random or complete distribution, and the composed test is not a timing of the full installed reconciliation process. A Rust MIME prototype could be worthwhile if production profiling shows parsing dominates. It must first match decoded text, Unicode, MIME alternatives, attachments and errors on a representative corpus: changing extraction can change thread hashes and recreate a large backlog.

A subsequent expanded read-only run parsed 100 messages in each of the same database-size bins using a deterministic rowid-derived ordering. Median / empirical p95 parsing times were 7.17 / 19.22 ms, 25.12 / 55.07 ms, and 107.48 / 303.29 ms, respectively; median actual file sizes were 25, 93 and 503 KB. There was one missing source file among 301 attempted; it was not included in the 300 successful parses. This stratified sample deliberately gives the three size bins equal weight, is not random, and excludes files larger than 4 MB. It therefore cannot estimate total production parsing cost. Larger messages deserve targeted profiling, but an extraction rewrite remains conditional on measured job impact and exact output parity.

The actual top 50 stale candidates were then parsed read-only, choosing a surviving registered alternative where necessary: all 50 parsed, including 36 via alternative paths. Total parsing was 1.30 s, median 10.78 ms and empirical p95 36.81 ms, with 25 attachments and 6.18 MB of file data. The extracted body differed from the currently stored body in 47 cases; that can be expected for stale extractions and does not itself establish which version is better. No changes were saved. These candidates are a single bounded backlog sample, not a bulk-import distribution or a full reconciliation measurement; after deploying the path fix, changed bodies can legitimately change thread hashes.

For Mail reconciliation, the sampled job found only one previously unknown file and no mtime-modified files while spending seconds enumerating the tree and selecting stale extraction candidates. This observation suggests prioritizing query/index and discovery measurements over MIME replacement for that particular cycle. A future controlled trial should distinguish normal idle cycles from bulk imports, re-extraction backlog and changed `.emlx` files, and include index creation, writes, restarts and recovery. Keep malformed MIME, nested alternatives, charset handling, attachment bytes, source/text hashes and Apple plist fields in the parity corpus. Never infer corpus-wide savings from a stratified per-file latency sample.

**GTE.** The actual deployed worker and manifest ran locally on MPS using synthetic text. Startup to ready was 4.91 s; median times were 0.018 s at 106 tokens (three requests), 0.055 s at 506 (three), 0.250 s at 2,006 (two), 0.712 s at 4,006 (two), and 2.091 s at 7,906 (one). Python-process RSS after inference was roughly 650–687 MB; GPU allocations and total unified-memory peak were not measured. This is real local inference, not email quality evaluation or a Rust comparison. The model is lazily started and many production decisions were cached. A wrapper rewrite would retain model execution and requires exact tokenizer, FP16, score and routing parity; prioritize other issues first.

**Usage.** On the same 2.55-GiB SQLite snapshot, the complete worker payload matched between current Node, an optimized Node variant and a Rust prototype for all-time, 30-day and 7-day windows, including list order. On 30 days, two-run medians were 8.51 s current Node, 6.68 s optimized Node and 3.91 s Rust; CPU medians were 8.49, 6.66 and 3.89 s. Process peak RSS medians were 89.4, 89.5 and 7.8 MB, excluding system page-cache accounting. At seven days, medians were 54.5, 52.4 and 13.2 ms. All-time results varied markedly with OS cache and load. A live `/usage?days=30` request in this study took 24.85 s the first time and 1.69 ms median for cached repeats; these are not interchangeable with the isolated worker results. Rust is a justified **integration candidate**, not yet a production-ready replacement: benchmark the HTTP path, concurrent writes, error/timeout handling, packaging and the Node-only optimization before choosing it.

The Node key-interning variant has since been applied to source and deployed in the bundled Usage worker. A further comparison against the Rust prototype on the real 30-day snapshot (12,209,678 calls) matched every summary field and list order. Cache and concurrent load made wall timings variable in that verification, so it should not be used as a new speedup estimate.

Release `2026-11-14T01-36-57-788Z-7304093e` includes the Mail path fix, Action Center gateway backoff and Node Usage optimization. After restart, host health, seven-day Usage and idle voice status returned HTTP 200; the first Action Center scan recorded one 402, one successful local embedding and 49 additional backoff deferrals, with zero recorded cost. Its logged wall time was 7.18 s; a single cycle is not a stable performance estimate. Following the first reconciliation, the top 50 stale candidates no longer had a missing primary path. The stale count changed from 19,943 in the earlier census to 19,851 in the later observation; intervening activity prevents attributing the whole difference to the fix. The guarded hash remains experimental; the indexes were deployed in the subsequent release.

**Gateway, host, voice and agent.** A warm generic local BGE embedding call through the gateway had a 26.2 ms median of two warm observations; the external model was already running. `/health` was 0.44 ms warm, `/system/status` 93.7 ms and `/voice/status` 0.42 ms, each with three warm observations. `/audit?limit=3` was 1.88 s first and 68.4 ms warm. These HTTP timings do not measure full voice calls, streamed agent turns or provider latency. The host depends on the Pi agent runtime; replacing or isolating that runtime needs a separate feature/parity study. No conclusion about Rust for the agent or voice can be drawn from these measurements.

## Recommended sequence

1. Monitor the deployed Action Center backoff, including retry visibility and pending work; measure again with provider availability restored.
2. Monitor the deployed Mail indexes and reconciliation path, including write overhead and re-extraction correctness. Profile Action Center's remaining scan after backoff and test future extractor-version upgrades.
3. Test the promoter's hash-first design end-to-end against the current path, including changed messages, concurrent mirror updates, malformed input, attachments, cache keys and error semantics. Keep it in TypeScript initially.
4. Integrate the Rust Usage worker only as a reversible experiment after HTTP parity, concurrency, timeout, resource and packaging tests. Compare against optimized Node, not only the current baseline.
5. Consider a Rust MIME parser only after a production profile and a golden corpus demonstrate both a meaningful performance opportunity and exact extraction behavior. Preserve source hashes and decisions across any change.
6. Retain the other MCP wrappers for now. Revisit a component only when a repeatable trace attributes material user-visible latency or memory to its implementation rather than SQLite, native libraries, model execution or external services.
